# Развёртывание Кадра с SQLite

## Схема

Браузер / будущее iOS-приложение → HTTPS reverse proxy → один Node.js-сервис → SQLite на постоянном локальном диске.
Сервис обращается к TMDB и SMTP. Linux использует стандартные fetch и Nodemailer; PowerShell нужен только для сетевого обхода в текущей Windows-среде.

SQLite работает в WAL, synchronous=FULL, foreign_keys=ON, busy_timeout=5000. Индексы предусмотрены для владельца/статуса карточек, email и сессий.
Пакеты изменений сохраняются атомарно. SQL-миграции применяются транзакционно и регистрируются в schema_migrations.
Доступ к базе изолирован в SQLiteRepository. Это граница будущей реализации PostgreSQL; полностью прозрачная замена без новой миграции не обещается.

## Docker Compose

1. Установи Docker на сервере, клонируй проект.
2. Скопируй .env.production.example в .env.production и заполни APP_ORIGIN (HTTPS-адрес без завершающего слеша), TMDB и SMTP.
3. Запусти docker compose up -d --build.
4. Направь HTTPS reverse proxy на 127.0.0.1:8080. В Nginx установи Host и X-Forwarded-For в реальный IP клиента, не передавая пользовательский заголовок как есть.
5. Проверь /api/health, письмо с кодом, два разных аккаунта, сохранение на двух устройствах, рестарт контейнера.

Пример для HTTPS-сервера Nginx с уже настроенным сертификатом:

~~~nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_read_timeout 180s;
}
~~~

Порт приложения опубликован только на loopback. TRUST_PROXY=1 допустим при такой изоляции и прокси, перезаписывающем X-Forwarded-For.
Если сервис открыт клиентам напрямую, TRUST_PROXY выключи. В production cookie имеет Secure и не работает по обычному HTTP.
APP_ORIGIN используется для защиты изменяющих запросов от чужого origin. Секреты не входят в образ.
Контейнер работает от пользователя node; named volumes сохраняют базу и backups между обновлениями.
Не выполняй docker compose down -v при обычном обновлении: это удалит volumes.
Проверка контейнера: docker compose exec kadr node -e "fetch('http://127.0.0.1:8080/api/health').then(r=>console.log(r.status))".

## Резервирование

В работающем контейнере:

~~~sh
docker compose exec -T kadr npm run backup -- /app/backups/kadr-YYYY-MM-DD.sqlite
~~~

Используется SQLite backup API: согласованный снимок включает данные из WAL. Обычное копирование одного файла работающей базы для резервирования не подходит.
Запланируй ежедневный запуск внешним cron и копирование снимков с сервера в отдельное защищённое хранилище. Автоматическая offsite-доставка пока не настроена.
Срок хранения определи по объёму, например 7 ежедневных и 4 недельных копии. Бэкапы содержат личные данные и должны быть закрыты от публичного доступа.

Для восстановления останови сервис, сохрани текущее состояние отдельно и замени файл базы проверенным снимком. При остановленном сервисе убери старые WAL/SHM только после сохранения текущей копии. Сохрани владельца файлов и запусти сервис.
Проверяй восстановление на отдельной копии периодически, не только наличие файлов.

## Рост

Это конфигурация для одного экземпляра приложения на одном сервере. Не размещай WAL-базу на NFS/SMB и не подключай к ней контейнеры разных хостов.
Чтение и запись могут идти параллельно, но писатель у SQLite один. Производительность зависит от диска и характера запросов; обещать фиксированное число пользователей без нагрузочного теста нельзя.
Если растут ожидания записи/SQLITE_BUSY, задержки запросов или нужны несколько хостов и автоматический failover, следующий шаг — PostgreSQL и перенос репозитория данных.
Не используй эфемерную файловую систему/serverless-хостинг без постоянного диска. Перед сменой формата базы требуется миграция данных и тесты изоляции аккаунтов.

## Ограничения проверки

Локально проверяются миграции, изоляция пользователей, транзакции, рестарт и резервная копия. Docker-образ и HTTPS-прокси нужно отдельно проверить на целевом сервере; внешний сервер сейчас не развёрнут.
